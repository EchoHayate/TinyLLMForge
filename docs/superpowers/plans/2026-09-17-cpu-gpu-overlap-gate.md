# 重叠门：CPU 算得动、GPU 也没被拖垮，但每层一次同步握手要吃掉 11% 的窗口

日期：2026-09-17
分支：`feat/kv-sparse-attention`
实验目录：`experiments/cpu_gpu_overlap/overlap-20260917-011042/`
工具：`tools/cpu_gpu_overlap_gate.py`、`tools/engine_step_cpu_interference.py`、`tools/run_cpu_gpu_overlap_remote.sh`

## 为什么要有这一门

前两门各自只量了一半：

- 选择器门 + 端到端门说明「选得准、答案保得住」（32-token 粒度，答案级约 3%，轨迹级约 11%）。
- CPU attention 门说明「算得动」（896 token / 64 线程 = 2.051 ms，窗口 12.113 ms）。

但「CPU 2.051 ms < GPU 12.113 ms」这句话默认了三件没量过的事：

1. **CPU 忙起来不会拖慢 GPU。** CUDA 的 launch 线程和 64 个 OpenMP 线程住在同一台机器上，抢的是同一批核。
2. **Q 下去、attention output 回来的往返是免费的。** 每层要一次，一步就是 2×36 次传输 **加上中间的同步**。
3. **真的有东西可以重叠。** 单序列里第 i 层的 attention 夹在 qkv_proj 和 o_proj 之间，它本身就在关键路径上。

这一门量前两件，并把第三件说清楚——它是调度问题，不是带宽问题。

## 结果

宿主机同期负载 load average ≈ 109，29 个用户在线，GPU7 被别人占满，本实验用 GPU2。

### 1. CPU 打满 64 线程时，GPU 掉多少

| 被测系统 | 单步（空载） | 单步（CPU 打满 64 线程） | 劣化 |
|---|---|---|---|
| HF python decode loop | 33.787 ms | 49.847 ms | **+16.06 ms（+47.5%）** |
| tinyvllm 引擎（CUDA graphs，B=1，8k） | 14.051 ms | 15.574 ms | **+1.523 ms（+10.8%）** |

这两行的差距本身就是结论：**launch-bound 的循环对宿主机争抢极度敏感，CUDA graphs 把这个敞口收窄了一个数量级。** 第一版我拿 HF 循环的 16.06 ms 去减 12.113 ms 的窗口，直接得出 `NOT_HIDEABLE`——那是拿一个系统的劣化去扣另一个系统的预算，结论是假的。引擎侧才是成本模型描述的系统，用引擎数：1.523 ms。

引擎空载 14.051 ms 与成本模型 `step_ms = c0 + (a + c1_eff·L_eff)·B` 在 B=1、8k 下的预期相符（c0 = 12.113 ms 加上单序列项），说明这个测法没有跑偏。

### 2. 每层一次 Q/output 往返要多少

| 方案 | 每步耗时 | 字节数 | 说明 |
|---|---|---|---|
| 逐层同步握手（36 层 × 一下一上） | **1.355 ms**（37.6 µs/层） | 1.18 MB | 调度真正需要的形态 |
| 全部融合成一对传输 | 0.068 ms | 1.18 MB | 数据依赖不允许，只作下界 |

拆解（直接探针）：裸 `synchronize` 5.0 µs、16 KiB H2D+sync 14.3 µs、16 KiB D2H+sync 11.8 µs。

**同样的字节数，逐层比融合贵 20 倍**——所以这 1.355 ms 全是每次握手的固定延迟，跟 PCIe 带宽没有关系（1.18 MB/步在 PCIe 上不值一提）。这是全套测量里最可执行的一条：优化方向是减少同步次数（CUDA event + 多流、提前一层发 Q、按层流水），不是压传输量。

### 3. 合起来算账

预算不能只写 `cpu_attn <= window`：GPU 劣化和握手延迟是**无条件支付**的，CPU 的 attention 时间只有真被别的 GPU 工作盖住才不计入。

```
无条件开销 = 引擎劣化 1.523 + 逐层握手 1.355 = 2.878 ms（占 12.113 ms 窗口的 23.8%）

轨迹级（896 token，2.051 ms）：headroom = 12.113 - 2.878 - 2.051 = 7.18 ms  → 装得下
答案级（256 token，0.416 ms）：headroom = 12.113 - 2.878 - 0.416 = 8.82 ms  → 装得下
```

## 结论与它不包含的东西

**可以装下，但先付 24% 的过路费。** 在最贵的轨迹级预算下仍有 7.18 ms 余量，所以到这一步为止没有一条硬伤能杀死这个方案。

必须明确不能由此推出的东西：

- **单序列内没有这份余量。** 第 i 层的 attention 在关键路径上，headroom 的前提是「CPU 的活能和不依赖它的 GPU 活重叠」。要真拿到，必须靠跨请求/微批流水（FastDecode、NEO 走的就是这条），或者提前一层把 Q 发下去。naive 的同步 per-layer 调用只会把 2.051 ms 直接加到每步上，不会藏起来。
- **1.523 ms 的劣化是在 load≈110 的脏机器上测的。** 两个 arm 都脏，差值仍然可用，但绝对值在干净机器上会变。
- **握手成本用的是 `torch.cuda.synchronize()`（整设备同步）。** 换 event/stream 同步应该更便宜，0.068 ms 的融合下界说明还有 20 倍的理论空间。这是下一个可动手的优化点，不是已经拿到的收益。

## 下一步

1. **把握手做成异步**：CUDA event + 独立流，提前一层发 Q，量一遍能从 1.355 ms 压到多少。
2. **跨微批流水的原型**：这是把 headroom 变成真实收益的唯一路径，也是唯一还没被测量过的核心机制。
3. **选择器自身开销**（gran=32 下 8 倍的 unit 数，min/max 摘要维护 + top-k），目前完全没量。
4. **干净机器复测**：现在所有 CPU 侧数字都带 load≈100 的底噪。
