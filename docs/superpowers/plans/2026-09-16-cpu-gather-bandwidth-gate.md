# CPU 侧 query-aware attention 的第一道闸门：散乱 gather 带宽与核数

日期：2026-09-16
作者：吴思天
工具：`tools/cpu_kv_gather_bandwidth.c`
原始数据：`experiments/cpu_gather_bandwidth/20260916-m5pro-18core.json`

> **读前提示**：正文是笔记本（Apple M5 Pro）上的第一轮测量，其中「必须按块选」「算术受限」
> 两条结论已被文末**服务器侧附录（Xeon 8336C）订正**。以服务器数据为准。

## 为什么先测这个

CPU offload + query-aware attention 这条线的成败押在一个从未测过的量上：**当 selector 只挑
k 个 token 时，CPU 从 host DRAM 抓取这些散乱块能拿到多少有效带宽**。规格书上的 DRAM 峰值是
顺序读数字，对散乱访问不成立。设计需要 ≥100 GB/s；低于约 80 GB/s 整条线就死了。

这个基准是**为了能杀掉方案而写的**，不是为了证明方案可行。

## 结论（先说）

**1. 搬运粒度是决定性变量，不是核数。** token 级（4 KiB）散乱抓取会砍掉 58–83% 带宽；
块级（≥128 KiB）几乎零损失。**selector 必须按块选，不能按 token 选。**

**2. 核数需求比预期低，因为瓶颈是算术而不是带宽。** attention 的算术强度只有 4 FLOP/byte，
而 CPU 的 FLOPS 太低，于是单核有效 KV 处理速率被算术卡在 12.5–37.5 GB/s，远低于单核
gather 能力 62 GB/s。**搬运只需 2–4 核，算术需要 4–15 核。**

## 实测数据（Apple M5 Pro，18 核，48 GB 统一内存，8 GiB 缓冲）

| chunk 粒度 | 1 核 SEQ | 1 核 RAND | 18 核 SEQ | 18 核 RAND | RAND/SEQ (1核→18核) |
|---|---|---|---|---|---|
| 4 KiB（1 token × 1 层） | 77.1 | **13.0** | 243.2 | **102.6** | **0.17 → 0.42** |
| 128 KiB（32-token 块） | 76.2 | **62.0** | 232.8 | **211.6** | **0.81 → 0.91** |
| 1 MiB（256-token 块） | 62.7 | 66.2 | 234.3 | 229.9 | ~1.00 |

单位 GB/s，取 3 次最好值。SEQ = 顺序读块，RAND = 打乱顺序读块（query-aware 选择的真实形态）。

### 读数

- **4 KiB 粒度是陷阱**：单核只有 13 GB/s，要靠 16–18 核才勉强堆到 100 GB/s。TLB miss 与
  预取器失效吃掉了大部分带宽。
- **128 KiB 粒度基本无损**：2 核 112 GB/s、4 核 188 GB/s。这是甜点——既避开带宽惩罚，
  又保留 256 个可选块（8192 / 32），选择粒度足够细。
- **1 MiB 粒度零惩罚但选择太粗**：8192 上下文只有 32 块，query-aware 的分辨力不够。
- **结论：block=32 tokens 是这一层级的正确取值**，而当前引擎的 `KVCACHE_BLOCK_SIZE=256`
  是按 HBM 调的，在这条路径上需要重调。

## 核数需求推算

attention 算术强度（Qwen3-8B，GQA 32 q-head / 8 kv-head，每 KV 元素被 4 个 q-head 复用）：

```
每 token 每层：K/V 各 2048 B，QK^T + AV = 32 × 128 × 2 × 2 = 16384 FLOP
16384 FLOP / 4096 B = 4 FLOP/byte
```

单核 gather 62 GB/s 若要不被算术拖住，需要 248 GFLOPS/核——远超任何 CPU 核。**所以必然算术受限：**

| 单核算力 | 单核有效 KV 处理速率 | 受限于 |
|---|---|---|
| NEON / AVX2 ~50 GFLOPS | 12.5 GB/s | 算术 |
| AVX-512 ~100 GFLOPS | 25.0 GB/s | 算术 |
| AVX-512 宽 ~150 GFLOPS | 37.5 GB/s | 算术 |

在 12.1 ms（GPU 读权重的窗口）内完成，B=19：

| k | k/L | 需处理 | 需带宽 | 核数需求（50 / 100 / 150 GFLOPS/核） |
|---:|---:|---:|---:|---|
| 432 | 5.3% | 1.21 GB | 100 GB/s | 8.0 / 4.0 / 2.7 |
| 605 | 7.4% | 1.70 GB | 140 GB/s | 11.2 / 5.6 / 3.7 |
| 812 | 9.9% | 2.27 GB | 188 GB/s | 15.0 / 7.5 / 5.0 |
| 1392 | 17.0% | 3.90 GB | 322 GB/s | 25.8 / 12.9 / 8.6 |

**可行区：6–14 核支撑 k=605–812（7.4–9.9% of L）。** 这比先前"12–35 核"的估计宽松得多，
原因是先前误把带宽当成瓶颈。

## 这对方案定价的影响

上一轮的族2 预算线（`B×k ≤ DRAM_BW × T / KVB`）需要修正：**约束不是 DRAM 带宽，而是
CPU 算力 ÷ 4 FLOP/byte**。于是：

```
B × k ≤ (n_cores × GFLOPS_per_core / 4) × T / KV_BYTES_PER_TOKEN
```

这意味着**量化在这条路径上的价值下降**：int8 减半 DRAM 流量，但如果瓶颈是算术且解压后仍按
fp32 算，FLOPs 不变，收益打折。若能直接在 int8 上做整数点积（VNNI / DP4A 类指令），才能同时
省带宽和省算术——**这是一个具体的、可验证的实现分支，必须先确认目标 CPU 是否支持 VNNI。**

## 局限（重要）

1. **本机是 Apple M5 Pro 统一内存，不是服务器 DDR5 + NUMA。** 绝对数字不可迁移。可迁移的是
   **RAND/SEQ 随粒度变化的规律**（TLB 与 DRAM row locality 的性质），这一条应当定性成立。
2. **未测跨 NUMA。** 服务器双路上若 KV 落错 socket，走 UPI 只有 30–50 GB/s，需要 `numactl`
   绑定后重测。
3. **未测与 Python 主循环的争抢。** 真实场景下调度/采样也在吃核。
4. **未用大页。** 4 KiB 粒度的惨状部分来自 TLB miss，大页可能明显改善——若真要走 token 级
   选择，这是必须先试的一招。
5. **A100 那台机器（10.232.195.203）当前 Kerberos 过期无法登录**，服务器侧数据待补。

## 下一步

1. Kerberos 恢复后在 A100 机器上重跑同一基准（`lscpu` / `numactl -H` 先存档），拿服务器
   侧的粒度曲线与可用核数。
2. 确认目标 CPU 是否有 AVX-512 + VNNI，决定量化分支是否可行。
3. 仍未解决的前置项不变：**有分辨力的质量门**（现有门禁全 100% 满分，测不出 top-k 漏检），
   以及 `a` 项标定。

## ⚠️ 污染声明（先说，因为它限定了下面每个数字的解释）

```
load average: 108.42, 103.87, 106.58   （128 线程的机器）
30 users logged in
各 node 空闲内存: 28.6 / 19.8 / 16.5 / 28.5 GB（共约 93 GB / 2015 GB）
```

**这台机器被别人占了八成以上。** 因此下面所有带宽数字都是**下界**，不是这台机器的能力。
8336C 每 socket 8 通道 DDR4-3200 理论约 205 GB/s，双路约 410 GB/s；我们测到 110 GB/s
只有理论值的 27%。空闲时应显著更高。

**同时要注意反向偏差**：争抢会把所有臂等比拖慢，从而把 RAND/SEQ 比值**向 1.0 压缩**。
所以下面"粒度惩罚很小"这个结论有可能被污染低估了，必须在空闲机器上复核。

（buffer 取 8 GiB 而非脚本默认值，因为最紧的 node 只剩 16.5 GB，membind 臂必须放得下。）

## 三条对主结论的订正

### 订正 1：「必须按块选，不能按 token 选」——在真 DDR 上不成立

笔记本上 4 KiB 散乱抓取只剩 17% 带宽，我据此下了"selector 必须按块选"的硬结论。
**服务器上同一测试是 0.63–0.90，惩罚只有 10–37%。** 原因是 M5 Pro 单核顺序读高达 77 GB/s，
散乱时损失的绝对量很大；而 8336C 单核顺序读只有 12–13 GB/s，本来就远离内存墙，散乱的相对
代价小得多。

**修正后的说法**：块粒度仍然更好且几乎免费，所以设计上仍应按块选；但**token 级选择并非
不可行**，只付 10–37% 代价。原先"这是实测硬约束"的说法过强，已撤回。这也说明用统一内存的
笔记本去外推服务器内存子系统是不可靠的，我当时把它当参照就已经越界了。

### 订正 2：NUMA 上要「铺开」而不是「钉住」

常规 NUMA 建议是把内存钉在本地 node。这里反了：`interleave=all`（110.6）比
`membind=0`（84.2）高 **31%**。原因是这条路径要的是**内存控制器总带宽**，铺满 4 个 node
才能把 4 组控制器都用上；钉在 node 0 只能用 1/4 的控制器，而且 `--cpunodebind=0` 把可用
逻辑核压到 32 个，128 线程还会 4 倍超订。

**设计含义**：KV 池应跨 NUMA node 交错分配，不要做本地性优化。这与直觉相反，值得写进设计。

### 订正 3：VNNI 存在 → 量化在这条路径上重新有价值

`avx512_vnni` 可用，所以 int8 可以走整数点积（VPDPBUSD），**同时省字节和省算术吞吐**
（int8 整数吞吐约为 fp32 的 4 倍）。这与 HBM decode 路径上的结论正好相反——那里 int8 因为
每步物化 fp16 瞬态 buffer 而斜率恶化 8.8–13×。

**同一个技术在不同层级上符号相反**，原因是瓶颈不同：HBM 上带宽不稀缺（只用 43% 峰值），
所以省字节没用而多出的解压开销全是净损失；CPU 侧带宽是唯一约束，省字节直接变成收益，
且 VNNI 让解压不再是额外代价。

## 修正后的设计预算

64 物理核提供约 6400 GFLOPS，而 110 GB/s × 4 FLOP/byte 只需 440 GFLOPS——**算术不再是约束，
带宽是唯一约束**（这也订正了本文正文基于 18 核笔记本得出的"算术受限"判断）。

| 模式 | 窗口 | 量化 | B×k 上限 | k @B=19 | k/L |
|---|---|---|---|---|---|
| 加速模式（藏进 GPU 读权重的 12.1 ms） | 12.1 ms | bf16 | 8,379–9,085 | 441–478 | 5.4–5.8% |
| **加速模式** | 12.1 ms | **int8+VNNI** | 16,758–18,171 | **882–956** | **10.8–11.7%** |
| 容量模式（用满现有 38.9 ms） | 38.9 ms | bf16 | 26,874–29,140 | 1,414–1,534 | 17.3–18.7% |
| **容量模式** | 38.9 ms | **int8+VNNI** | 53,748–58,279 | **2,829–3,067** | **34.5–37.4%** |

对照：现状 HBM 全量 `B×k = 155,648`（100% of L），单步 38.85 ms。

## 核数：非约束（回答最初的问题）

| 线程数 | 16 | 32 | 64 | 128 |
|---|---|---|---|---|
| interleave 128 KiB RAND | **102.4** | 105.5 | 104.1 | 110.6 |

**16 线程（8 物理核）已达 102 GB/s，再加核几乎没有边际收益。** 这台机器有 128 线程，
所以"CPU 核太少"这个担心可以排除；而且只要 8 个物理核，在共享机器上也拿得到。

## 闸门判决：**通过**

即便在 load=108 的污染下界上，`int8+VNNI` 也能在 GPU 读权重的 12.1 ms 窗口内支撑
**k≈900（约 11% 上下文）**，容量模式下可到 **k≈3000（约 37%）**。这两个数都落在 query-aware
稀疏的常见工作区内，因此这条路线**不该在这一步被杀掉**。

## 仍未解决的前置项（没有变化）

1. **有分辨力的质量门**——最关键。k/L≈11% 意味着扔掉 89% 的 token，而现有门禁全 100% 满分，
   结构上测不出 top-k 漏检。**在补上之前，上面所有 k 值都无法验收。**
2. **`a` 项标定**——决定天花板是 8.7× 还是 49.7×，且 CPU 协调会推高它。
3. **在空闲机器上复核本次测量**——当前是污染下界，且 RAND/SEQ 比值可能被争抢压向 1.0。
4. **未测大页**（THP=madvise）。若最终走 token 级选择，大页是必须先试的一招。
5. **未测与 Python 主循环争抢**。真实场景下调度/采样也吃核。
