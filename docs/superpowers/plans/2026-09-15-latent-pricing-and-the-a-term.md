# latent 方向的统一定价，以及唯一还没标定的那个量

日期：2026-09-15
分支：`feat/kv-sparse-attention`
前置：`2026-09-15-graph-path-kv-baseline.md`（graph 路径基线 + int8 臂被证伪）

## 这份文档要解决什么

上一份文档给出了 graph 路径基线，并把"容量轴"基本判死（≤1.5×）。结尾建议的下一步是
"KV8 + Quest"。**这个建议是低价值的，已作废**：用户和另一个 Agent 都已经把 KV8 和 Quest
做完并拿到收益。也就是说"字节轴"在"量化 + 块稀疏"这个具体形态上已经被吃过一轮，不需要我
再测一遍。

但这件事本身反过来暴露了一个更值得处理的问题：**我一直在一个个地测具体方案，却没有把所有
latent 方案放进同一个坐标系里定价。** 定价公式一旦写出来，大部分方案不需要跑实验就能判死或
判活，而且会立刻暴露出"唯一还没标定、却决定整条线天花板"的那个量。

## 统一定价公式

全部参数来自实测（Qwen3-8B、A100、graph 路径、pinned pool）：

```
step_ms = c0 + (a + c1_eff * L_eff) * B

  c0      = 12.1 ms        每步固定成本，主要是权重读取，被 B 摊薄
  a       = ? ms/seq       与 L 无关的 per-sequence 项  <-- 唯一没标定的量
  c1_eff  ∝ bytes_per_token   每 token KV 字节数（bf16 GQA 实测 147,456 B/token）
  L_eff   = 实际参与 attention 的 token 数
  B       = 并发序列数，受 KV 预算约束
```

任何 latent / 压缩方案，本质上只能动三个地方：

| 动哪里 | 机制举例 | 效果 |
|---|---|---|
| `B`（同预算塞更多序列） | 纯容量压缩 | 只吃 `c0` 的摊薄 |
| `c1_eff`（每 token 更少字节） | 量化、低秩、MLA、更少 KV 头 | 线性压 `c1_eff * L` |
| `L_eff`（更少 token） | Cartridges、context 压缩、latent memory、块稀疏 | 线性压 `c1_eff * L` |

**关键结构性事实：`a` 是压缩碰不到的项。** 压缩只能压 `c1_eff * L_eff` 这一项，压到 0 之后
剩下的就是 `c0 + a*B`，那就是天花板。

## 三条轴的定价（全部由实测参数推出，无需新实验）

以 L=8192、bf16、pinned 640-block pool 的**实测**撞墙点 482.74 seq/s 为固定分母 1.00×
（刻意不用模型重算基线，否则 `a` 的假设会同时污染分子和分母，让比值看起来比实际稳定）：

| 方案 | 撞墙 B | 吞吐 @ a=0.042 | 相对基准 | 吞吐 @ a=0.238 | 相对基准 |
|---|---|---|---|---|---|
| 基线 L=8192 bf16 | 19 | 489 seq/s | 1.01× | 446 seq/s | 0.92× |
| **只压字节** 2×（L 不变） | 38 | 959 seq/s | **1.99×** | 807 seq/s | **1.67×** |
| **只压 token 数** 4×（L→2048，字节不变） | 70 | 1798 seq/s | **3.73×** | 1329 seq/s | **2.75×** |
| **同时压** 4× token + 2× 字节 | 141 | 3352 seq/s | **6.94×** | 2022 seq/s | **4.19×** |

基线行不等于 1.00× 是模型自曝的误差：a=0.042 下高估 1.3%（单一 c0 锚在 L=8192），
a=0.238 下低估 8%。这个残差量级就是下面所有数字的可信精度上限。

三个读数：

1. **token 数轴始终强于字节轴**，因为压 token 数是**乘性**的：既降斜率（`c1*L` 里的 L），
   又升容量（每序列占更少 block）。而压字节只在同一项上做线性削减。
   但**优势幅度强烈依赖 `a`**：a=0.042 时 3.73/1.99 = **1.87×** 领先，a=0.238 时只剩
   3.73→2.75 对 1.99→1.67，即 **1.65×** 领先。`a` 越大，"缩短上下文"能买到的东西越少——
   因为 `a*B` 这部分与 L 无关，压 token 数压不到它。
2. **两轴叠乘（6.94× / 4.19×）**，不是相加。这才是 latent 方向值得做的量级。
3. 所以 **latent 相对量化/稀疏的结构性优势是：它是唯一能同时压两个轴的东西**。一个 latent
   向量既可以代表多个原始 token（压 `L_eff`），又可以是低维的（压 `c1_eff`）。量化只能压字节，
   块稀疏只能压 token 数。这是个真研究论点，不是工程 trick——上一轮我跑偏到 layout/并发时，
   缺的正是这个论证。

⚠️ 注意 "只压字节 2× = 1.99×" 这一行**在本引擎不可实现**：实测 int8 臂斜率反而恶化 8.8×，
因为 KV4/KV8 decode 会把命中块物化成完整 fp16 瞬态 buffer。1.99× 是理想化上界。
"压 token 数 4× = 3.73×" 用的是同 pool 下 L=2048 的**实测点**做代理，因此隐含假设是
"压缩后任务质量不掉、且压缩本身零成本"——这同样是上界。

## 唯一还没标定的量：`a`，它单独决定天花板是 8.7× 还是 49.7×

对 `slope(L) = a + c1*L` 求解，现在有两个互相矛盾的估计：

| 来源 | a | 绝对天花板 `1000/a` | 相对 L=8192 基线 |
|---|---|---|---|
| 本次两点外推（L=2048 / 8192 斜率） | 0.0417 ms/seq | 23,981 seq/s | **49.7×** |
| GATE A 的 M2 拟合 | 0.238 ms/seq | 4,202 seq/s | **8.7×** |

两者差 **5.7×**。这不是学术细节，它直接决定方向决策：

- 若 `a ≈ 0.238`：即使完美 latent 压缩（`c1*L → 0`），上界也只有 8.7×；扣掉实现损耗、
  质量损失和编码成本，现实收益可能落到 3~4×。那 latent 这条线的性价比要重新评估。
- 若 `a ≈ 0.042`：上界 49.7×，值得投入训练成本去搏。

`a` 同时决定的第二件事常被忽略：它决定 **token 轴相对字节轴的优势幅度**（1.87× vs 1.65×，
见上表）。也就是说 `a` 不只调整天花板高低，还调整"该优先压 token 数还是压字节"这个排序的
置信度。如果标定出来 `a` 偏大，latent 相对量化的结构性优势会同步变薄，而不只是天花板变低。

`c1` 这边反而是一致的（本次 0.167 us/token vs GATE A M2 的 0.161 us/token，两个不同网格），
所以分歧全在 `a`。原因大概是两次拟合的 B 范围不同：GATE A 网格里 B 最大只到 32，`a*B` 与
`c1*L*B` 高度共线，`a` 基本是被挤出来的残差项，不可信；本次是拿两个 L 的斜率相减外推，
同样是弱识别。**两个都不是为了测 `a` 而设计的实验。**

### 标定实验设计（待跑，约 15 分钟）

让 `c1*L` 退居次要、`a` 成为主导：取**小 L、大 B**，逐 L 拟合斜率，再对 5 个
`(L, slope)` 点回归求 `a`（新增 3 点 + 已有 2048/8192 两点），这样 `a` 是内插得来而非外推。

```bash
RUN_TAG="a-term-calibration-$(date +%Y%m%d-%H%M%S)" \
CUDA_DEVICE=<idle> EXECUTION_PATHS_OVERRIDE="msgraph" KV_BLOCKS=640 \
SWEEP_GRID="256:64,128,192,256;512:64,128,160,192;1024:32,64,96,120" \
WARMUP_STEPS=24 bash tools/run_kvcapacity_step_scaling_remote.sh sweep
```

网格已按 pinned pool 的整块预算核算过（632 可用 block）：L=256 每序列 2 block（B=256 用
520 block）、L=512 每序列 3 block（B=192 用 584）、L=1024 每序列 5 block（B=120 用 608）。
判读：若三个小 L 的斜率随 L 明显收敛到 0.04 附近，则 `a` 小、天花板高；若收敛到 0.2 以上，
则 GATE A 的 M2 是对的，天花板只有 8.7×，需要重新评估整条线。

**阻塞**：Kerberos ticket 已失效（`klist: Cache not found`），远端 A100 机器当前 SSH 不可用，
需要先恢复认证才能跑。

## 顺带一个值得知道的数字：KV 读取只跑到峰值带宽的 43%

```
c1 = 0.1667 us/token,  bf16 GQA = 147,456 B/token
  -> 有效 KV 读带宽 = 885 GB/s
  -> A100 80GB HBM2e 峰值 ~2039 GB/s  =>  43%
```

这有两层含义：

1. 它解释了**为什么 Quest 那类"少读 block"的手段能拿到收益**：瓶颈确实在 KV traffic 上。
2. 但 43% 说明 traffic 之外还有约 2× 的 kernel 效率水分（page table gather、GQA head 广播、
   block_size=256 的访存模式）。**这意味着"压字节"的理论收益会被 kernel 效率吃掉一部分**——
   字节减半不等于时间减半，除非 kernel 本身接近带宽极限。这也是 int8 臂失败的同一个病根的
   另一面。

## Pre-mortem：这条线仍然可能是死的，5 个理由

1. **`a` 标定出来很大**（0.238 量级）→ 天花板 8.7×，扣掉损耗后不足以支撑一个研究方向。
   这是最可能的死法，也是为什么标定必须先做。
2. **质量侧从未验证**。上面所有定价都假设"压缩后任务质量不掉"。4× token 压缩的 3.73× 是用
   L=2048 的真实测点代理的，但那是**真的 2048 token 的任务**，不是"被压成 2048 的 8192 token
   任务"。质量掉了，定价全部作废。
3. **编码成本未计入**。Cartridges 类方法需要离线自学习/训练，per-corpus 成本；agent 场景若
   上下文每轮都在变，离线编码摊不平。这是它真正的门槛，不是收益不够。
4. **本引擎缺基础设施**。字节轴需要 fused dequant-in-attention kernel；低秩 latent 需要原生
   低秩 attention。没有它们，任何方案测出来都是瞬态 buffer 的开销（int8 臂已证）。
5. **6.95× 是双轴理想叠乘**。现实中同时拿到 4× token 压缩和 2× 字节压缩且质量不掉，需要两个
   独立难题同时解决；只拿到一个的话回到 2~3.7×，那和"把 kernel 效率从 43% 修到 80%"这种
   纯工程手段是同一量级——而后者不需要训练、不需要研究、也不会掉质量。这是这条线最尴尬的
   竞争对手。

## 下一步的正确顺序

1. **先标定 `a`**（15 分钟，需恢复 Kerberos）。它决定天花板是 8.7× 还是 49.7×，是所有后续
   投入的前提。在这之前不要开始任何实现工作。
2. **再做质量 gate，而不是速度 gate**。速度侧的定价现在已经基本清楚了（上界 6.95×，主要
   不确定性就是 `a`）；真正没验证的是"压缩后还能不能做对任务"。速度实验再跑十轮也回答不了
   这个问题。
3. 若 `a` 小且质量 gate 过得去，才谈实现路径（fused kernel / 原生低秩 attention）。

## 附录：与已完成的 KV8+Quest 工作交叉验证——字节轴在两条路径上都是负收益

你提到 KV8 和 Quest 已经做完并拿到收益，所以不必重跑。我没有重跑，而是把工作区里已有的
那批产物（`experiments/kvcapacity_step_scaling/20260914-kv8quest-final-*`、
`20260915-kv8quest-*`）直接读了，用来和我这轮 graph 路径的 int8 结论对账。结论是：
**两边的速度数据互相印证，而且都是负收益；那份工作自己的门禁结论就是 `NO_GO_KV8_QUEST`。**

### 1. 斜率：两条路径独立测出几乎相同的恶化

| 来源 | 路径 | bf16 斜率 | int8 KV 斜率 | 恶化 |
|---|---|---|---|---|
| 本轮 pool640 baseline | **graph** | 1.407 ms/seq | 12.327 ms/seq | 8.8× |
| 已完成的 KV8 工作 | **eager** | 0.964 ms/seq | 12.506 ms/seq | 13.0× |

int8 斜率在两条完全不同的执行路径上落到 12.3 / 12.5 ms/seq——几乎同一个数。这是强证据：
恶化来自 KV4/KV8 decode 把命中块物化成完整 fp16 瞬态 buffer 这个实现事实，与 graph/eager
无关。不是我的测量偏差，也不是他们的。

### 2. "收益"的分母是 KV8 自己，不是 bf16

那份 gate 报告的亮点数字是 `Quest/KV8 = 0.562×`、"B=19 excess-latency recovery 56.3%"。
但分母是 **KV8 臂**。Quest 找回的是 KV8 自己造成的损伤的一半多。换成 bf16 做分母：

| B | bf16 ms | KV8 ms | KV8+Quest ms | KV8/bf16 | KV8+Quest/bf16 |
|---:|---:|---:|---:|---:|---:|
| 4 | 41.6 | 65.9 | 82.5 | 1.59× | **1.99×** |
| 8 | 44.2 | 114.4 | 81.6 | 2.59× | **1.84×** |
| 12 | 49.1 | 166.3 | 96.4 | 3.39× | **1.96×** |
| 16 | 51.7 | 215.9 | 122.2 | 4.18× | **2.37×** |
| 19 | 56.3 | 252.8 | 142.2 | 4.49× | **2.53×** |

**KV8+Quest 在每一个 cell 上都比什么都不做的 bf16 慢**，撞墙点 B=19 慢 2.53×。
他们自己的吞吐读数也是一致的：bf16 峰值 337.67 seq/s（CAPACITY OPEN），
KV8 只有 75.17 seq/s（CAPACITY WEAK，0.22×），KV8+Q16 133.65 seq/s（0.40×）。
而那份 gate 的最终分类就写着 `NO_GO_KV8_QUEST`，失败项 `quest_not_faster_in_every_cell`。

所以"已经拿到收益"这个印象，大概来自把 `Quest/KV8 = 0.562×` 读成了对基线的加速。
按那批数据自己的口径，字节轴在本引擎是负收益，且已被其作者判为 NO_GO。

### 3. 质量门其实没有分辨力（这条对后续更重要）

两份报告的质量表全是 100.0% / 100.0% / 100.0%，depth 0.00→1.00 全满，delta 全 0.0 pp。
这不叫"质量无损"，这叫**任务饱和、门禁没有分辨力**——一个所有臂都满分的指标无法区分任何
方案，包括无法发现真正的质量退化。合成 fixed-needle workload 对 Qwen3-8B 太容易了。

这是个必须在做 latent 之前补上的洞：latent / Cartridges 这类压 `L_eff` 的方法，风险主要
就在质量侧（压掉的 token 里有信息）。如果沿用这套 100% 饱和的门禁，任何 latent 方案都会
"通过质量门"然后在真实任务上塌掉。**下一步的质量门必须先自证有分辨力**：即在一个已知会伤
质量的对照臂（比如激进截断、random-drop 50% token）上必须明显掉分，否则该门禁不可用。

### 4. 对本文定价结论的影响

- 表中"只压字节 2× = 1.99× / 1.67×"这一行，现在有**两条路径的实测**共同证明它在本引擎
  不可达，且方向是反的。它只能作为"若有 fused dequant-in-attention 内核"的理想上界。
- 因此 **token 数轴（压 `L_eff`）是目前唯一还活着的轴**，这反而加强了本文的主论点，
  但加强的方式是"别的路都堵了"，不是"这条路已被验证"。
- 下一步优先级不变，但顺序应调整：`a` 标定（决定天花板 8.7× 还是 49.7×）之后，
  **先建一个自证有分辨力的质量门**，再谈任何 latent 实现。速度侧已经不缺数据了。
