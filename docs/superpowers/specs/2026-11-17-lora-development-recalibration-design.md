# LoRA 必要性：开发校准重设计

日期：2026-11-17。

状态：**待批准的研究设计稿。用户已同意继续设计下一步；本文件不是新题库、
代码实施、模型运行、训练或远程启动许可。**

## 1. 为什么重设计

已封存的 D01–D04/base/text 实验完成了 16 次生成和 64 次最终用例执行，
两组都 4/4 题全对；首轮 16 条公开反馈也全部 pass。独立原始证据审查通过，
但按预定规则，结论为 `INCONCLUSIVE_CALIBRATION / both_arms_all_pass`。
它证明固定链路可运行，未展示反馈纠错，也无法判断参数更新的增量。

依据：`experiments/lora_necessity/20261117-development-remote-results.md`。
本次重新核验其 closeout 的 73 项文件绑定；不改原文件、原规则或原结论。

下一版先回答两个问题：

1. 新开发任务上，模型的首轮答案是否存在可被可靠测试揭示的语义错误？
2. 对同一首轮候选，公开测试反馈相比同样一次无结果续答，有何帮助或伤害？

第三个问题——LoRA 是否优于获得相同可信示例的文字记忆——仍是后续独立阶段。
本设计不将前两个问题的正结果当成第三个问题的答案，也不称其为 RSI。

## 2. 选择与边界

| 路线 | 能解决什么 | 局限 |
| --- | --- | --- |
| 只换更复杂的开发题 | 检查原四题的满分是否源于覆盖过窄 | 两轮改善仍可能只是多一次推理 |
| 新任务加配对续答对照，推荐 | 同时观察错误覆盖与反馈相对额外推理的贡献 | 每个任务/记忆条件需三次生成，而非两次 |
| 完整仓库与依赖环境中的修复 | 更接近实际工程工作 | 改变任务和执行范围，暂不与本轮混合 |

保持任务类型为确定性的单函数修复。规格、错误实现和公开测试作为任务输入，
不要求特定补丁，不按参考源码相似度评分。不改成答案选项、事实复述或格式恢复。
不通过降低 text 的示例完整性、缩短其输出或给它更少工具机会制造权重优势。

保持经核验的 Qwen3-8B、greedy、同一模板、4096 输入 token 和 256 输出 token
上限作为拟议比较条件。没有“题目更复杂就自动扩预算”的规则。是否能容纳
新题面、原八例、完整首轮候选及两种续答，须在将来独立的真实 tokenizer
核验中确认。长度不适配说明本草案的可执行性尚未成立，不证明方法无效。

旧 driver 的 eager/no-cache 设置不改变；计时只代表该固定研究路径，
不是主推理引擎吞吐。真实模型工作仍只在远端，不接入 scheduler、KV cache、
CUDA Graph 或请求内参数热更新。

## 3. 新开发材料

拟定 **12 个全新的开发任务，四个主要修复机制各三题**。沿用 v1 的八个可信
监督示例作为唯一历史信息源，不把这些新任务的答案添加到示例或训练数据。
开发任务不作为任何适配器的训练样本。

输入沿用有界、无外部依赖的 JSON 可表示值：严格整数、ASCII 字符串、布尔、
null、列表和固定字段记录，不引入浮点误差判分、导入、文件、网络或时钟。
集合/事件流长度不超过 32，输入整数绝对值不超过 1000；离散枚举的域宽
不超过 32。每题再明确有效值、字段、空输入与事件前置条件；不能靠参考
实现决定未写清的语义。预期异常若存在，必须写进规格和 outcome 类型。

四种主要机制仍为 bounds、reset、multiplicity、order；需要跨分支、
状态与重复/并列输入的联合约束，不能只把符号判断换一个名字。
以下固定拟议结构与检验意图，不冒充已完成的题面、答案或难度校准：

| ID | 主要机制 | 拟议任务结构 | 关键联合作用 |
| --- | --- | --- | --- |
| C01 | bounds | 按到达顺序处理带过期时间的容量预订，输出每次是否获准 | 恰好过期先释放；恰好满容量允许；拒绝不占容量 |
| C02 | bounds | 按块读取含控制段的逻辑字节区间，返回各数据块的覆盖长度 | 逻辑端点、空交集与不计入地址的控制段 |
| C03 | bounds | 对有界整数域上的加权区间构造离散差分并还原各点负载 | 左闭右开、裁剪到域内、负权重与端点相接 |
| C04 | reset | 对交错事务事件维护各事务暂存值，提交产生结果、回滚丢弃 | 重用事务 ID、交错事件与事务终止后的局部状态 |
| C05 | reset | 对按键交错的序列号事件计算连续缺口告警，重连开启新段 | 每键前值、重连和重复序列号不继承旧缺口 |
| C06 | reset | 解析扁平整数流中的分组与组内重置标记，输出每组峰值 | 两级生命周期、连续标记与组末刷新 |
| C07 | multiplicity | 在有限数量券库存下顺序满足多项订单，库存不足整单拒绝 | 重复券需求、部分检查失败时库存回滚、后续订单 |
| C08 | multiplicity | 合并多份来源清单，按“出现在至少指定数量来源中”输出标签 | 同一来源重复不多投票，跨来源出现保留计数 |
| C09 | multiplicity | 计算带重复值记录的等值连接匹配总数，同时排除相同来源配对 | 两侧频次乘积、来源内扣除与多来源重复 |
| C10 | order | 对键值更新维护有限容量最近使用列表，返回最终键序列 | 更新已有键移动而非复制、淘汰与重新插入 |
| C11 | order | 汇总多来源投票并排序候选，平票依首次有效投票顺序 | 无效票不占先后位置、重复有效票与稳定并列 |
| C12 | order | 按优先级选择受每类配额约束的记录，再按原输入序号返回 | 选择顺序与输出顺序不同、同优先级与配额耗尽 |

这不是生产缺陷采样或预训练未见证明。结构是否真正不同、完整正确函数
能否在 256 token 内表达，均须后续数据审阅验证。尤其检查 C01/C07 的
资源准入近似性、C04/C05 的按键状态近似性，以及 C10 与历史顺序题的重叠。
不能靠不同 ID 或不同家族标签自动认定独立。

编写顺序必须是：结构审核 → 逐题精确规格与合法输入域 → 用例和手工推导 →
独立参考实现与错误变体 → 静态交叉审阅 → 另行获准的动态/长度核验 → 冻结。
每题恰好两条公开用例和六条私有评分用例，输入不得重复。各联合约束均须
有具名用例覆盖；八例不是完备性保证。原始错误实现和至少两个行为不同的
错误变体，必须有明确拒绝见证，不能只检查“某个变体至少错一次”。

结构或长度审核失败可以在任何新模型结果产生前修订并留痕；完整版本必须
重新冻结。模型输出后不替换个别题、不追加题、不从更大池中只留失败题。
12 题全保留为固定分母。若仍然饱和，接受再次校准不足，而不是无限调题。

## 4. 谁判断纠错是对的

反馈与评分均由受信控制端基于冻结规格和用例判断，不让生成模型自己裁决。

- **答案来源**：手工推导公开见证及私有期望值；第二审阅者按规格复核。
  两个参考实现采用不同的计算分解，交叉核对固定用例；不得把同一实现
  换名字作为独立依据。两者一致仍不是数学完备证明。
- **反例检查**：原错误程序及两个错误变体应被各自见证拒绝；正确参考实现
  应在全部八例通过。规格歧义、推导冲突或动态结果不一致时不准入整批，
  不能将异常 oracle 的结果发给模型当作“你答错了”。
- **公开反馈**：仅发送公开 case ID 与 pass/mismatch/受限执行错误状态。
  不发送私有输入、期望值、模型打分、完整 stdout 或宿主错误消息。
- **最终判断**：全部模型生成结束后，对首轮及两种续答分别评分；私有评分
  不参与本批任何提示、样本选择、停止生成策略或训练目标。
- **评审身份**：第二 agent 不是独立人工签核。没有人工审阅时明确保留
  “助手构建、经所列检查的受限程序修复题库”，不称权威 benchmark。

本轮不注入虚假反馈。故意错误的 oracle 需要独立的鲁棒性实验，不能与可信
反馈效果混合。后续发现测试或参考答案错了，保留旧结果并标记协议失效；
纠正 oracle 后的结果属于新版本，不能静默覆盖旧结论。

## 5. 同一首轮候选的两条续答

记忆条件仅有 `base` 与 `text`：

- base 不含历史示例。
- text 含 v1 原八例的完整同一字节投影，需绑定其输入与渲染摘要。

每个任务/记忆条件：

1. 生成首轮候选 `initial` 一次并持久化原始字节。两条续答共用这份候选，
   不能各自重新采样一个更方便的首轮答案。
2. 格式合法时，运行两条公开用例一次；非法源码不执行，记录格式反馈。
3. 从相同原任务消息和首轮 assistant 消息分叉：
   - `feedback`：附加下述共同修订指令和真实公开结果。
   - `retry`：附加同一修订指令及固定
     `{"kind":"results_withheld"}`，不附加任何执行结果。
4. 两条分支各调用一次生成，不传递对方的答案或成绩，不挑 best-of-two。
   首轮通过也照常运行；`retry` 不谎称测试通过、不打乱标签。
5. 先完成全部 12 题两种记忆条件的生成，再开始独立评分阶段。
   评分按任务、记忆条件、`initial/feedback/retry` 顺序处理三份已冻结候选，
   每份执行相同八例。两条分支不得使用或共享对方的 KV/可写状态。

`retry` 仍能阅读原任务中的公开测试并自行推理，因此测的是**执行结果可见性
相对无结果续答的增量**，不是“有无测试知识”。反馈内容和 token 数不同，
故相同调用机会不是相同实际算力。无意义填充 token 不作为公平性修补。

两分支的共同修订指令固定为：
`Return the final complete function, even if you believe the first candidate is correct.`
不用旧指令中的 “Public-test feedback follows” 暗示 retry 已获得测试结果。
这种 v2 消息变更不回写 v1 提示或旧封存证据。

固定顺序：C01–C12；奇数题 base/text，偶数题 text/base。
对 `(题序号-1)` 模四为 0/1 的任务，base 先 feedback 后 retry，text 相反；
模四为 2/3 时，base 先 retry 后 feedback，text 相反。两种记忆条件各有
六次先执行每种分支；两种记忆次序与两种 base 分支次序的四个组合各出现
三次。不得按首轮是否出错改变次序。

所有逻辑 ID 均绑定新的研究版本、run/task/memory/candidate-role/case，
与旧 round=1/2 身份区分。一次已消费的逻辑尝试不得换目录重新提交。

| 计划数量 | 固定上限/分母 |
| --- | ---: |
| 任务 | 12 |
| 任务×记忆条件 | 24 |
| 首轮生成 | 24 |
| feedback/retry 续答生成 | 24 + 24 |
| 总生成调用 | 72 |
| 公开反馈机会 | 24 |
| 公开候选执行 | 最多 48 |
| 三种候选的八例评分位置 | 576 |
| 全部候选执行 | 最多 624 |

576 是用例执行位置，不是独立样本；每种记忆/候选条件只有 12 个任务。
初始格式无效及后续失败导致的未执行位置仍保留；绝不把计划数量写成实测。
诊断共用首轮，因此不会给部署反馈流程额外记上 retry 的推理成本来误导比较。

## 6. 指标与预先停止规则

对每种记忆条件和每个任务，用八例全部通过定义候选的功能成功。
主报告仍保留全部 12 题，另报两条公开与六条私有用例的分层结果。
固定候选状态如下，附带每个用例的完整性和失败类型，不能靠“不是 pass”
推导 fail：

- `PASS`：八例均有有效、正常且符合期望的结果。
- `SEMANTIC_FAIL`：源码有效，至少一例有效正常结果与期望不同；这个反例
  足以证明该候选不能全通过，但其他用例缺失仍须单独记录，不能补造。
- `EXECUTION_FAIL`：没有已观察语义反例，但有确认的格式拒绝、
  program_error/output_limit 或候选时限失败。已确认语义反例与这些错误
  并存时保留 `SEMANTIC_FAIL` 并另记执行错误，不用二选一删除信息。
- `UNKNOWN`：既没有足以确认失败的有效证据，也没有八例全通过证据；
  如七例通过、最后一例未完成。基础设施超时不等于已证实候选超时。
- `INVALID_EVIDENCE`：候选身份、oracle 或证据存在矛盾；不进入有效配对。

候选超时只有已绑定控制器证明候选已启动并触发候选时限时，才是确认的
执行失败；未完成启动、断线或缺失回执只能保持未知。整批完整性另算，
单个已知反例不允许用来宣布其他缺失工作已完成。

必须报告：

1. initial、feedback、retry 各自的已观察通过数 / 12，以及上述各状态数量。
   未知保留在 12 的计划分母中，但不是确认失败，也不称完整正确率。
2. initial→feedback 与 initial→retry 的语义配对转移：错→对、对→错、
   对→对、错→错。只纳入两端均为 PASS/SEMANTIC_FAIL 的任务，报告共同可观察
   任务数及按状态排除的任务数；两端八例还必须完整、正常且无并存执行错误。
   纠错率的分母是该配对子集中初始语义错误数，
   退化率的分母是其中初始通过数，零分母为 null；不能分支之间偷换分母。
   另报全五状态交叉表，让 PASS→EXECUTION_FAIL 等真实功能损害仍清楚可见。
3. feedback 与 retry 的配对净增：
   `feedback通过/retry失败的任务数 - retry通过/feedback失败的任务数`。
   此处功能失败仅含 SEMANTIC_FAIL/EXECUTION_FAIL，且必须按这两种失败类型
   分列。UNKNOWN/INVALID_EVIDENCE 不进任何已知输赢格子。
   既报告净值，也报告两类不一致数，不用净值掩盖改坏。完整 12 题净增只在
   全部所需评分完成、证据有效、两端结果均已知时给出，否则为 null。
   可另报 `observed_subset_net_count`、共同已知任务数和缺失身份；
   该部分计数不得标成完整 12 题收益或据此判方法优劣。
4. 首轮功能错误中有多少被公开反馈揭示，有多少只在私有评分暴露。
   此项只统计已观察语义反例；初始执行失败、未知与无效证据另列。公开
   “未揭示”只在两条公开结果都正常且通过时成立，公开回执缺失不能算漏检。
   统计单位是任务，不把同一题的多个失败用例重复算作多次纠错机会。
5. 逐机制分布、格式/程序/超时问题、未执行/未知记录，以及分层实测成本。

用于机会校准的“首轮语义错误”指格式有效、八例执行完整正常且至少一条
评分结果与期望不同；
格式错误、超时和基础设施故障不是语义错误。对这些非正常结果单列数量，
不靠它们凑出“模型终于会犯错了”的难度门槛。

以下是本草案提出、尚未执行的工程预警门槛，不是统计功效保证：

1. 身份、来源、oracle、隔离或记录矛盾：`INVALID_PROTOCOL`。
2. 生成/评分缺失、必要成本未知或基础设施中断：
   `INCONCLUSIVE_INCOMPLETE`。
3. 下列首轮机会条件不满足：
   `INCONCLUSIVE_CALIBRATION`：
   - base 与 text 各自首轮须有至少 3 个全通过任务、至少 3 个语义错误任务。
   - 每种记忆条件至少 2 个语义错误任务被公开用例揭示，且覆盖至少两个
     主要机制；不是依靠一个函数的两个失败输入凑数。
4. 完整且全部工程条件满足：`DEVELOPMENT_DIAGNOSTIC_USABLE`。

同时保留所有原因；优先级不删除其他失败信息。继续/中止规则明确为：

- 语义 mismatch，以及回执、身份、成本和子进程退出/回收均已确认的
  program_error/output_limit/候选超时，是候选级结果。记录后继续其余
  计划分支、用例和任务，不因负面结果减少计划工作，也不给失败项补跑。
- 格式无效的候选零执行，八个评分位置显式记为
  `not_executed_invalid_source`，候选为已知 EXECUTION_FAIL；这是协议规定的
  完整格式拒绝，不是八次执行失败，也不是八份丢失回执。它不能进入语义
  配对，但可进入已知功能损害统计。首轮格式拒绝同样零公开执行，按规定
  仍给两条续答机会，不移除后续任务。
- 生成失败、基础设施/安全/身份异常、必需回执或成本无法确认、子进程
  未确认退出/回收时立即中止整次运行，保留证据和尚未完成的位置，不重试。
  未知工作不会为保持诊断可用而补成成功或失败。

格式拒绝的完整性由明确拒绝记录与零执行证据建立；不能因没有 child receipt
而伪造回执，也不能把已发生但丢失证据的执行误写成这种可预期的零执行。

**不要求 feedback 必须胜过 retry，也不要求 text 胜过 base 才保留结果。**
零/负差异及 feedback 完全修复都可以是有效诊断。续答的通过数不参与首轮
机会校准，不设 feedback 或 retry 的最终得分下限/上限。
例如初始两组各六对六错、公开错误覆盖合格且全部执行正常时，base 的
feedback=2/retry=6 与 feedback=6/retry=2 都是可用的诊断；前者的真实损害
不能用“校准不可用”掩盖。上述第 4 项不表示方法已获益或下一阶段已获准。

最终得分的满分/零分另外作为描述性结果保留。text-feedback 若 12/12 全过，
表示本开发集合上该最终任务指标没有剩余的参数增益空间，不表示反馈对照
无效。新 LoRA 研究的任务/收益门槛要另行定义，不能倒过来改变本次诊断标签。

确认的格式拒绝、程序错误、输出超限与候选超时作为执行问题分项计数，
不以这些后续负面结果撤销诊断可用性；它们也不算作首轮语义错误来凑门槛。
候选失败后若回执/成本不完整，仍由第 2 项判不完整。此处把 v2 的证据有效性、
首轮机会与最终方法表现分开，不回写 v1 原校准规则及其已结束结果。

12 个任务和单一固定生成设置不支持总体显著性或长期稳定性结论。
不把 576 用例或同一题的两条分支当独立样本，不据此生成夸大的置信区间。

## 7. 成本与后续 LoRA 问题

按生成、公开核验、最终评分、加载/完整性检查和外层墙钟分层记录；
保存输入/输出 token、forward、峰值 allocated/reserved 和原始计时。
未知为 null，包含关系的计时不相加当总成本。

分别列出本次诊断的全部开销，以及 initial+feedback、initial+retry 两条
候选使用路径的组成。公开测试实际为共同诊断运行过，不能把 retry 的实测
总账写成“完全没花核验成本”；可单列其不需要结果的反事实路径，但不得
冒充额外实测。私有评分是评估成本，不把它当线上必要推理成本。

若未来另行批准权重比较，仍以 `lora_text` 对 `text` 为主要比较，
两者获取逐字节相同可信示例；`lora` 对 `text` 只回答压缩历史信息的辅助问题。
必须另行固定未用于改设计的迁移/保留任务、训练配置、精度/退化阈值和成本
比较，不自动套用本文件的 12 题或诊断分支作为训练/收益验收集。
训练 loss 下降只证明训练路径信号，不代替任务改善、保留能力或净收益。

## 8. 旧数据、实现与许可

原 v1 批次保持结束。按照原 pilot 第 6 节，本次根据其结果重设计后，
**v1 的迁移/保留材料不再作为新方案的独立验证集**，即使其新模型输出未曾
打开，也不借用这些题反向挑新开发任务。未来确认性比较需要重新冻结新任务。
本轮只读取既有设计与封存证据，不运行旧 1,416 条验证，不打开旧后续成绩。

当前组件的硬编码边界包括四个 D ID、八个 episode、两轮、v1 数据 pins，
以及只绑定第二轮的 final plan。不能仅把 4 改成 12 就称 v2 已支持。
后续应另建版本化的任务投影、分叉排程/关联和三候选评分合同，独立验证
身份错绑、未提供结果分支泄漏、评分提前、无效候选分母和中断语义。
复用已经接受的观察式生成/隔离执行原语，也必须重新审查实际运行包；
不改已封存 v1 源文件来通过旧 checksum。

实施顺序应为：用户批准本设计 → 结构/题目与答案核验设计 → 纯组件实施及
合成回归 → 新数据动态/长度核验 → 精确包审查与独立运行许可 → 单次新实验。
本草案不生成 run ID、不准备 transport、不消费任何新旧远程入口。
GPU 数量、流程时限和目标运行身份在未来准入前冻结；不能沿用旧运行许可
自动启动 72 次生成。也不恢复已撤销的聚合内存/磁盘预算或断线自动清理条件。

本轮不写执行代码，不训练、连接远端、安装、提交或推送。
`benchmark_eligible`、`formal_evaluation_ready`、`net_benefit_established`、
`isolated` 全部保持 false。

## 9. 草案自查与待批准事项

- 纠错对象：模型生成的首轮答案，而不是把预置错误程序当成模型犯错。
- 判断来源：冻结规格、逐例推导、参考/变体检查与独立评分，不是自评。
- 信息对照：首轮相同，结果可见性不同；没有用额外首轮采样混淆反馈效果。
- 研究单位：12 任务；24 首轮与 48 续答；48 公开执行上限与 576 评分位置。
- 数据边界：不训练开发题，不读取后续成绩挑题，不把 v1 旧题称新独立评测。
- 负面结果：校准再失败、反馈无增量或改坏均照实保留；不要求 LoRA 赢。
- 实施边界：这是方案，不是题库已验证、组件已支持或远端正在运行。

需要用户批准的是：采用此配对续答路线、12 题结构方向与工程预警门槛，
随后才进入新数据和实现计划。设计批准本身不授权模型或远程执行。
