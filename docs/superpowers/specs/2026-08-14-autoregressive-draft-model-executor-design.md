# Autoregressive Draft-Model Proposal Executor Design

**Date:** 2026-08-14

**Status:** Proposed continuation design

## Objective

Add a model-independent autoregressive learned-draft executor that lets an
independent dense decoder participate in the existing source-neutral
speculative runtime and reuse the generic proposal-KV lifecycle coordinator.

The first concrete backend is Qwen3 dense decoder. The intended target is the
existing Qwen3.5 hybrid runtime, so this path exercises two materially
different model structures:

- Qwen3 dense causal decoder as the independent learned drafter;
- Qwen3.5 hybrid recurrent/full-attention decoder as the target.

This design does not claim that the second learned structure is established
until a source-attributed real Qwen3 checkpoint passes an Engine-level exact
greedy correctness gate.

## Current State

The repository already provides:

- a source-neutral `ProposalExecutor` protocol and registry;
- a batch-native first-target plus tail verifier;
- target-KV prepare, commit, and rollback transactions;
- `ProposalKVCache` for proposal-side physical ownership;
- `ProposalKVLifecycleCoordinator` for proposal registration, batched
  finalize, rollback, release, and authority evidence;
- a Qwen3.5 native-MTP executor using the coordinator;
- Qwen3 dense model loading and tensor-parallel execution;
- host n-gram and SAM adapters as non-learned sources.

The missing production component is an independent autoregressive model
executor. Existing `tools/draft_model_schema.py` is profiler-only and must
not be treated as a runtime learned drafter.

## Proposal Token Semantics

The existing runtime proposal convention is retained:

```text
proposal token 0:
  first target token produced by the target first-token forward

proposal tokens 1..Q-1:
  tokens generated by the proposal source
```

An independent draft model therefore performs at most `Q - 1` learned decode
steps. For `MAX_PROPOSAL_TOKENS=4`, it executes at most three draft steps.

The proposal-side KV transaction stages the inputs used for those learned
steps:

```text
first_target_token, proposal_token_1, ..., proposal_token_(Q-2)
```

The number of staged entries is `Q - 1`. If the verifier accepts `A`
proposal tokens, the number of proposal-KV entries committed is:

```text
max(A - 1, 0)
```

This is the same lifecycle formula already used by Qwen3.5 MTP. No
`ProposalKVCache` finalize API change is required.

## Considered Approaches

### 1. In-Process Autoregressive Draft Executor

Selected.

Load the independent draft model in the target ModelRunner process, give it
an isolated physical KV store, and register a model-independent
autoregressive proposal executor in the existing registry.

Advantages:

- no host transfer of logits or hidden states;
- proposal KV participates in the existing atomic lifecycle;
- first-target fusion and batch-native verification remain unchanged;
- Qwen3 and future dense decoder backends can share the executor;
- source timing can include the actual learned draft forward cost.

Costs:

- additional model weights on every participating rank;
- a dedicated multi-layer proposal KV allocation;
- explicit tokenizer and vocabulary compatibility validation;
- a later TP4 policy decision for replicated versus sharded drafter weights.

### 2. Sidecar Draft ModelRunner

Rejected for the first integration.

A separate process could reuse the existing Qwen3 ModelRunner and return
tokens over RPC. This isolates memory, but adds dispatch and synchronization
latency, complicates proposal-KV ownership, and cannot naturally join the
current Engine publication transaction.

### 3. EAGLE-Style Hidden-State Drafter

Deferred.

It may have better economics, but requires a target-specific hidden-state
contract and an attributable compatible checkpoint. No such checkpoint is
present in the current workspace. Implementing an untrained or synthetic
head would not satisfy the learned-structure gate.

## Architecture

Create:

```text
tinyvllm/engine/autoregressive_draft_executor.py
```

The file contains model-independent orchestration:

```python
@dataclass(frozen=True)
class AutoregressiveDraftPrefillRow:
    transaction: ProposalKVTransaction
    token_ids: tuple[int, ...]
    positions: object


@dataclass(frozen=True)
class AutoregressiveDraftDecodeRow:
    transaction: ProposalKVTransaction
    step: int
    input_token_id: int
    position: int


class AutoregressiveDraftBackend(Protocol):
    @property
    def device(self): ...

    def prefill_batch(
        self,
        rows: tuple[AutoregressiveDraftPrefillRow, ...],
    ) -> None: ...

    def decode_step_batch(
        self,
        rows: tuple[AutoregressiveDraftDecodeRow, ...],
    ) -> tuple[object, ...]: ...


class AutoregressiveDraftProposalExecutor:
    ...
```

The executor owns:

- target-prefill token observation and chunk continuity;
- per-sequence draft bootstrap state;
- exact-Q grouping and batch order restoration;
- proposal transactions and materialization through the injected backend;
- tensor-parallel greedy token agreement;
- proposal timing and tensor-free authority evidence;
- one `ProposalKVLifecycleCoordinator`.

The backend owns:

- model-specific forward calls;
- model-specific attention context construction;
- binding physical proposal KV tensors to model attention layers;
- returning one one-token logit row for every decode row in input order;
- logits shape, dtype, device, and finite-value checks.

The backend does not own transaction registration, accepted-prefix commit,
rollback, release, Engine publication, or scheduler state.

`supports_batch=True` requires backend calls to be batch-native. The executor
may partition rows by `exact_q` and decode step, but it must not implement a
batch by invoking one backend forward per sequence.

## Qwen3 Backend

Create:

```text
tinyvllm/engine/qwen3_draft_backend.py
```

The first backend wraps `Qwen3ForCausalLM` and a dedicated multi-layer
physical slot store.

The physical store allocates one token slot across every draft-model layer:

```text
K: [layers, capacity, block_size=1, local_kv_heads, head_dim]
V: [layers, capacity, block_size=1, local_kv_heads, head_dim]
```

One logical proposal slot ID identifies the same token position across all
layers. Reserving or releasing a slot therefore affects the complete
multi-layer draft KV entry.

Because the proposal store fixes `block_size=1`, a proposal slot ID is also
the paged-attention block ID. The backend binds each Qwen3 `Attention` module
to `[capacity, 1, local_kv_heads, head_dim]` K/V slices for that layer. It
uses the existing temporary attention context with:

- token-level `slot_mapping`;
- committed plus visible staged slot IDs as the block table;
- one-token decode query length;
- proposal-local KV only;
- target KV offload and target residency managers disabled.

The backend must derive `local_kv_heads` from the instantiated Qwen3
attention modules after tensor-parallel partitioning. It must not allocate
the global `num_key_value_heads` shape on each rank unless the entire
drafter is explicitly in the separately approved replicated-TP mode.

No proposal physical slot may alias a target KV block or target offload slot.

## Prefill and Bootstrap

`observe_target_prefill()` consumes the shared
`TargetPrefillObservation` row and persists only:

- sequence ID and epoch;
- token IDs;
- positions;
- final-chunk flag.

The registry's shared observation validator still requires a target-hidden
payload because the row schema is shared with native MTP. The independent
draft executor may validate its row count, but it must neither retain nor
read target-hidden values. Its proposal capability therefore remains
`requires_target_hidden=False`.

Chunks must:

- start at position zero;
- be contiguous and non-overlapping;
- retain one sequence epoch;
- contain integer token IDs;
- have positions exactly equal to the expected contiguous range;
- have target-hidden row count equal to token count without inspecting the
  payload values;
- end with exactly one final chunk.

At the first proposal call, the executor bootstraps the draft KV cache with
the observed prompt token sequence. Unlike Qwen3.5 MTP, it does not shift
target hidden rows. It performs a normal draft-model prefill over the prompt.
The prefill materializes prompt KV only. Any final prompt hidden state or
logit produced internally is not returned to the executor and is not a
proposal token: proposal token 0 remains the target-produced
`first_target_token`.

Bootstrap uses a proposal-KV transaction:

```text
begin(prompt_token_count)
-> backend.prefill_batch()
-> mark_materialized(prompt_token_count)
-> prepare_finalize(accepted_proposal_tokens=prompt_token_count + 1)
-> commit_finalize()
```

The `prompt_token_count + 1` argument is a bootstrap-only encoding that
causes the unchanged `ProposalKVCache` formula to commit all
`prompt_token_count` staged entries. It is not verifier acceptance evidence,
must not be exposed as an accepted proposal count, and must be wrapped by a
named bootstrap helper rather than duplicated at call sites.

The committed proposal cache then represents the complete observed prompt.
Bootstrap is performed at most once for a `(sequence_id, sequence_epoch)`.
Bootstrap failure aborts the transaction, retains the complete immutable
pending prompt, and permits an explicit retry only when the cache reports no
active transaction or finalize ticket and no committed prompt slots.

For a batch containing multiple unbootstrapped sequences, the executor:

1. validates every pending prompt before allocating any slot;
2. begins all bootstrap transactions;
3. performs one `prefill_batch()` call;
4. marks every transaction fully materialized;
5. prepares every bootstrap finalize ticket;
6. commits the prepared tickets.

A failure before commit aborts or rolls back every still-owned bootstrap
transaction in reverse order. A commit failure uses the same poisoned-runtime
boundary as proposal finalize; bootstrap must not invent partial-recovery
semantics.

## Proposal Execution

For each `ModelRunnerProposalInput`:

1. Compute:

   ```text
   exact_q = min(
       remaining_output_tokens,
       input max proposal tokens,
       executor max proposal tokens,
   )
   ```

2. If `exact_q == 0`, return an empty proposal without a transaction.
3. Start a proposal-KV transaction with `exact_q - 1` staged entries.
4. Initialize proposal tokens with `first_target_token`.
5. Group rows by `exact_q`; for each step shared by the active rows:
   - write the current input token into the step's staged KV slot;
   - expose committed slots plus the staged prefix to attention;
   - execute one `decode_step_batch()` forward for all active rows;
   - require one logit row per input row in the same order;
   - select the exact greedy token with the existing TP agreement helper;
   - append the selected token.
6. Mark all staged entries materialized.
7. Register the proposal through `ProposalKVLifecycleCoordinator`.

For `exact_q == 1`, the transaction owns zero staged entries, is marked
materialized with count zero, and is still registered because the non-empty
proposal contains `first_target_token`. Finalization commits zero proposal
KV entries under the unchanged accepted-prefix formula.

Any model, shape, collective, or registration failure aborts still-owned new
transactions in reverse order.

## Tokenizer and Vocabulary Contract

The executor may be registered only when all of the following are fixed and
validated:

- target tokenizer artifact fingerprint;
- draft tokenizer artifact fingerprint;
- target vocabulary size;
- draft vocabulary size;
- tokenizer class and normalization configuration;
- ordered token-to-ID mapping fingerprint over the full vocabulary;
- BOS, EOS, PAD, and every generation stop-token ID;
- model and checkpoint fingerprints.

The first production gate requires byte-identical tokenizer artifacts when
available, plus exact ordered token-to-ID mapping and special-token equality.
Equal vocabulary sizes alone are insufficient. Token remapping, vocabulary
projection, lossy conversion, or post-hoc replacement is forbidden.

The Qwen3-0.6B checkpoint may be used only if its tokenizer contract exactly
matches the selected Qwen3.5 target checkpoint.

## ModelRunner Registration

Configuration gains source-neutral independent-draft settings rather than a
Qwen3-only runtime branch:

```text
autoregressive_draft_enabled
autoregressive_draft_model
autoregressive_draft_backend
autoregressive_draft_max_proposal_tokens
autoregressive_draft_gpu_slot_capacity
```

`autoregressive_draft_backend` selects a registered backend factory; the
first allowed value is `qwen3`. Unknown backends fail configuration before
model weights or proposal slots are allocated.

`ModelRunner` construction may use a Qwen3-specific backend factory, but the
registry descriptor remains generic:

```python
ModelRunnerProposalExecutorDescriptor(
    executor_id="autoregressive-draft",
    capabilities=DraftCapabilities(
        source_type="independent_draft_model",
        supports_batch=True,
        requires_target_hidden=False,
        requires_target_logits=False,
        max_proposal_tokens=4,
        execution_domain="model_runner",
        requires_proposal_lifecycle=True,
        requires_full_token_history=False,
    ),
)
```

Generic Engine, Scheduler, verifier, target-KV transaction, and proposal
finalize RPC code must not branch on Qwen3, checkpoint names, or the source
type.

## Tensor Parallel Boundary

### TP1

The first implementation and real-checkpoint correctness gate use TP1.

### TP4

TP4 is outside the first implementation acceptance criteria and is a
separate promotion gate. Before that gate is run, configuration must fail
closed when `tensor_parallel_size != 1`; silently replicating or partially
constructing the drafter is forbidden.

A later TP4 design amendment must choose exactly one mode:

- shard the Qwen3 drafter using its existing tensor-parallel layers; or
- explicitly replicate the drafter on every rank when memory accounting
  proves the replication is intentional and affordable.

The selected mode must be explicit configuration and authority evidence; it
must not be inferred from checkpoint shape or rank-local success.

Every rank must execute the learned draft path and participate in exact
greedy agreement. Broadcasting rank-0 fixture tokens or skipping draft
forwards on nonzero ranks is not valid TP4 evidence.

## Error and Release Semantics

- stale prefill epochs fail before draft KV mutation;
- duplicate or non-contiguous prefill chunks fail closed;
- bootstrap failure aborts all new physical slots;
- proposal failure aborts the current transaction;
- partial batch registration uses coordinator cleanup;
- finalize prepare failure performs coordinator rollback and abort cleanup;
- commit failure poisons the speculative runtime through the existing Engine
  boundary;
- sequence release is rejected while a transaction is active;
- successful release clears committed draft KV and model-specific pending
  state;
- no failure path mutates target KV, target offload counters, verifier
  selection, side-state selection, or Scheduler output.

## Evidence

Authority snapshots remain tensor-free and record:

- source type and backend identity;
- model and tokenizer fingerprints;
- tensor-parallel rank and size;
- prefill/bootstrap rows;
- selected draft tokens;
- proposal transaction rows;
- prepared ticket count;
- active transaction count;
- committed and released proposal slot counts;
- draft forward timing;
- zero live slots after release.

Timing evidence must distinguish:

- checkpoint construction and loading;
- prompt bootstrap;
- proposal forward;
- proposal finalize;
- target verification.

Checkpoint construction and loading are not included in steady-state TPOT,
but must still be reported.

## TDD and Local Validation

The first implementation plan must use dependency-light fake backends before
any GPU run.

Focused tests cover:

1. capability and registration validation;
2. mixed empty and non-empty batch order;
3. chunked prompt observation and contiguous bootstrap;
4. exact proposal token convention beginning with `first_target_token`;
5. `Q=1..4` staged-entry counts;
6. partial acceptance committing exactly `max(A - 1, 0)` entries;
7. rollback releasing the complete staged suffix;
8. multiple accepted rounds appending committed slots without replay;
9. stale epoch, duplicate sequence, malformed logits, and collective failure;
10. active transaction release rejection;
11. final release returning every physical slot;
12. tensor-free authority snapshots;
13. coexistence of Qwen3.5 MTP and autoregressive executors in the generic
    registry;
14. unchanged Engine proposal finalize and publication behavior;
15. TP>1 fail-closed behavior before the separate TP4 design is implemented;
16. tokenizer equality rejecting same-size but differently ordered
    vocabularies and mismatched special-token IDs;
17. block-size-one physical layout and per-layer cache binding;
18. bootstrap retry only from a zero-owned-slot, zero-active-transaction
    state.

Static tests also require generic runtime files to remain free of Qwen3 and
Qwen3.5 source branches.

## Real Checkpoint Gate

Local synthetic tests establish only executor and transaction contracts.
They do not establish a second learned structure.

The first real gate requires:

- a source-attributed Qwen3 checkpoint and immutable file hashes;
- a source-attributed Qwen3.5 target checkpoint;
- exact tokenizer and vocabulary compatibility evidence;
- TP1;
- BF16;
- greedy temperature zero;
- `MAX_PROPOSAL_TOKENS=4`;
- batch 1 first, followed by batch 4;
- exact output-token parity against target-only decode;
- proposal acceptance and transaction evidence;
- zero proposal KV leaks;
- no extra target forward;
- real draft-model forward counts on every measured proposal;
- explicit separation of proposal KV bytes from target KV bytes.

The gate records both tokenizer artifact hashes and the ordered
token-to-ID mapping hash. A missing artifact hash must be explained and
cannot be replaced by vocabulary-size equality.

Performance is not a pass criterion for the initial correctness gate.

## Promotion Boundary

Completion of the local implementation proves:

- one generic autoregressive learned-draft executor exists;
- Qwen3 dense execution can reuse the proposal lifecycle contract;
- Qwen3.5 MTP and Qwen3 draft paths share generic registry and transaction
  infrastructure.

It does not prove:

- a real second learned structure, until the checkpoint gate passes;
- TP4 correctness;
- 4K, 16K, or 32K learned-draft correctness;
- batch-4 or multi-sequence correctness, unless separately executed;
- TPOT, TTFT, throughput, or memory improvement;
- reduced target KV H2D traffic;
- KV8 or KV4;
- production readiness;
- Phase 1 completion.

The full Phase 1 gate remains `NOT_PROMOTABLE` until all objective matrix
requirements are covered by real evidence.
